  How a system ends up doing that

  The realistic mechanisms all put a filter upstream of pagination:

  - An INNER JOIN where a LEFT JOIN was intended. Upload rows live in staging;
  serving joins them to resolved company records to populate company_id and
  company_name. Rows whose identity resolution failed have no company record, so
  the join silently discards them. This is the single most common way this
  happens.

  enrichment matches domain/name against the account graph → 6 fail to resolve →

  table still holds 223; nothing reads it.

  :cursor ORDER BY company_id, NULL never satisfies the predicate — SQL NULL
  comparisons are never true. Those rows become permanently unreachable, and the
  scan terminates normally without them.
  - A partial index (... WHERE company_id IS NOT NULL) used to order the scan,
  so an index-only plan never visits the NULL rows.

  chain, a legitimate partial final page, and a quiet truncated: false.

  The defect: a replaying service inflates the plan when no declared size is 
  passed

  build_campaign_plan(ReplayingLoader(L1), ...)      # no expected_row_count
    companies=215  deliverables=860      (should be 209 / 836)

  Root cause is in paging._resolve: with expected_row_count is None it returns
  served — every row the service handed over, replays included. Then in
  build_inventory:

  rows returned=446 (served) vs rows_deduped=223
  identified companies  =203   <- correct count, but provenance doubled:
                                  company-junction-foods -> ('row-1001#0',
  'row-1001#1')
  unidentified companies=12    <- should be 6
    ['unidentified:row-2401#0', 'unidentified:row-2401#1', ...]

  unique_row_labels disambiguates the replayed copies, and for unidentified rows
  the key is built from the label — so one uploaded row becomes two companies.
  203 + 12 = 215, × 4 = 860.

  Two things make this worse than a miscount. It reintroduces the customer's
  original complaint — duplicate creative — through a new path. And it breaks
  the traceability invariant C2 exists to guarantee: row-1001#0 and row-1001#1
  assert that two uploaded rows exist where the upload has one. The served
  reading doesn't just risk being wrong, it's inconsistent with the conservation
  property the rest of the design depends on.

  Blast radius is contained but not zero. make demo, make verify and make test
  are unaffected — demo.py:26 and the test both pass expected_row_count. And
  evaluate_campaign_coverage catches it (6 companies never campaigned), so it
  can't pass the check. But build_campaign_plan is the product path, and
  aj_work/audit.py:161 calls collect_rows without the count while line 109
  passes it — inconsistent within one file, so audit.py --loader ReplayingLoader
  reports 215.

  The fix is one line: default rows to fresh rather than served when no declared
  size is supplied. Verified — the deduped reading alone gives exactly 209.

  reasoning isn't wrong: a repeated page might be legitimate, and discarding
